## 二、**我们比引擎更对**的**两处**（这是唯一硬的对比）
（下面第 1、2 条是**引擎会给出的错值**；第 3 条是另一类——"它有分步、但求导那一段它没有"——顺带记在这一节。）

⚠️ 这两条不是"HiPER 做得差"，是**libqalculate 在边界上会给出看着像答案的错值**——
而 HiPER 大概率用的是另一套内核，**它在这两处的行为我没有量过**。

⚠️ **同一条纪律还挡住了一条更诱人的写法**（2026-10-12 记）。我们的**引擎**在三个具体案例里比**我们自己那条
`double` 回退**更对，三例都**有测试钉着**：

| 输入 | `double` 回退会给的 | 引擎给的 |
|---|---|---|
| `123456789012345678 - 123456789012345677` | 当成误读，显示成下溢的 `0` | `1` ✓ |
| DEG 下的 `tan(1e12)` | 因 `arg*pi/180` 的舍入超差而丢掉引擎的正确答案 | ✓ |
| `1/3000000000pi` | `1.061033e-10`（应用自己的读法） | `1.047198e-9` ✓ |

（证据：`test/core/math/engine_expression_test.dart` 与
`test/domain/calculator_engine_translation_test.dart`。）

⚠️ **但它不进上面那张表** ✗：那需要写下「**HiPER 大概也用 double，所以我们也比它更对**」——
而那是一个**我没有量过的推测** ✓，与本节开头那句警告是同一条纪律 ✓。所以它留在这里，
作为一条**内部**记录（我们比自己更对 ✓），而不是一条**对外**主张 ✗。

### 1. `factor(x^2 + 2x + 1)`

| | 结果 |
|---|---|
| 引擎 `qalc` 5.12.0 | **`x^2 + 2x + 1`**（把输入原样退回，kind `SYMBOLIC`，**屏幕上放行**） |
| 我们 | **`(x + 1) × (x + 1)`** ✓ |

### 2. `roman(10000)` / `roman(-1)` / `roman(0)`

| 输入 | 引擎 | 我们 |
|---|---|---|
| `roman(10000)` | `"10000"`（把输入当字符串还回来） | 拒绝，说明规范范围 |
| `roman(-1)` | `"-I"`（**凭空造的写法**） | 拒绝 |
| `roman(0)` | 数字 `0`（**类型都变了**） | 拒绝 |

### 3. 求导分步

HiPER 的分步是**十进制 / 表达式模式**的（把 `1+2×3` 拆成"先乘后加"），
**对求导不给步骤**——这一条是"它有分步、但这一块它没有"。
而我们的求导分步**每一步都写清用了哪条法则**，并且**三类不会的情况诚实停下**
（表外函数、不可导点、两边定义不同的拼写）。

## 三、明确的短板（**我们没有**）

> ⚠️ **本节在这一轮之后变短了**：`算术分步` 原本是这里唯一一条**明确的能力缺口**，
> 已于 `9272048` 落地（`1 + 2 * 3` → `1 + 6` → `7`，纯 Dart、12 条测试）。
> 剩下的两条是**工程规模**问题，不是"它有我们没有"的设计缺口。


1. **拍照解题** —— 要接第三方服务，不是一个量级的事。
2. **自然语言输入** —— 要写解析器。
4. **多变量求导** —— 工具收 `diff(y^2, y)`，但混合偏导、多元函数没有。
5. **化简** —— 恒等式那一层做了（去乘 1、去加 0），
   **合并同类项、展开括号、任何排版决定都没做**（那些有取舍）。

## 五、性能与体积基线（2026-09-30 **第一次量**）

⚠️ **这一节只有我们自己的数，HiPER 那一侧是空的**——我手上只有它的手册，没有它的安装包，
也不打算去下别人的 APK 来量。**所以这一节不构成对比，它是基线**：
**任何"优化"要能说清有没有变好，都得先有这个数。**

### 1. APK 体积 —— ⚠️ **我第一版把这里写成"发现一处 2 倍的浪费"，那是错的**

我量了 `flutter build apk --release`（**三 ABI 合包**，72.2 MB），又量了
`--split-per-abi` 出来的 arm64 那一份（32.6 MB），于是写下"55% 是白给的、x86_64 是模拟器专用的浪费"。

**先看一下 `docs/release_checklist.md` 就不会写这句话**——那份清单第 21 行与第 30 行**写的就是**
`flutter build apk --release --split-per-abi`。**发布流程早就在用分片构建了**；
72.2 MB 那个合包是**裸跑一条命令**的结果，**没有人发布它**（README 里那个 `universal` 是
"一份包要盖住所有 ABI 时"才用的可选项）。

**我把"没有人发布的那个构建"当成了"我们发布的东西"，然后把它与发布的东西比。**
这是本次会话里**第三次**同一类错（前两次：拿 CLI 当库、把中止的脚本当成跑完了）——
而三次的形状完全一样：**从一个没核过的前提往下推，且推得越顺越不会回头核。**

| 构建 | 体积 | 谁在用 |
|---|---|---|
| `--split-per-abi` 的 arm64-v8a | **32.6 MB** | **发布给真机的就是它** |
| 同上，armeabi-v7a | 19.0 MB | 老设备 |
| 同上，x86_64 | 22.4 MB | 模拟器 |
| 裸 `--release`（三 ABI 合包） | 72.2 MB | **没有人发布这个**；README 里的 `universal` 是可选项 |

**所以体积这一项：没有发现浪费，也没有优化余地——流程本来就是对的。**
唯一新增的信息是**这几个数**（此前没有记录），而它们的用处是**将来若变了能看出来**。

### 2. 冷启动

| 构建 | `am start -W` 的 TotalTime |
|---|---|
| **debug**（三次） | 2122 / 1749 / 1757 ms |
| release | **未测**（这一轮没装 release 包——装它会替换掉机器上那个用于验证的 debug 包） |

⚠️ **debug 的数字不代表用户看到的**：debug 走 JIT，release 走 AOT，通常快好几倍。
**把 1.75 s 当成"我们的启动速度"是错的**，所以这一格写的是"未测"而不是那个数。

### 3. 求值延迟（宿主实测，桥自己的调用序列）

探针：`qalc` 5.12.0，同一串调用（`unlocalizeExpression` → `calculate(EXACT/APPROXIMATE)`），
`-O2`，逐条计时：

| 表达式 | 耗时 |
|---|---|
| `2+2`（**进程里第一次调用**） | **16.072 ms** |
| `integrate(x^2,0,1,x)`（第二次调用） | 16.480 ms |
| `sqrt(8)` | 0.597 ms |
| `multisolve([x+y=3, x-y=1], x, y)` | 0.618 ms |
| `exp(-x^2)` | 0.540 ms |
| `factor(123456)` | 0.438 ms |
| `sin(x)` / `sin(1)` | 0.12 ms |
| `2^2000` / `100!` | **0.02–0.05 ms** |

⚠️ **第一次调用那 16 ms 不是算术的代价。** 它是**懒加载 `loadGlobalDefinitions()`**——
应用自己的代码里就写着这件事（"启动后的第一次提交最容易触发（那一次包含懒加载）"），
而这份实测**正好印证了那句话**：第二、三次调用（`integrate` 那种重活）也在同一个量级，
而真正算得慢的 `2^2000`、`100!` 反而是 **0.02–0.05 ms**。

**所以冷启动那 1.75 s 里有一次 16 ms 的定义加载，而它只发生一次。**
这条数对"要不要预热引擎"这类优化是直接有用的——**而此前它只是个说法，现在它有数了。**

### 5. 设备侧延迟：探针修好之后量到的两个数

第一次没测成，原因是**轮询时只拉了 `nekocalc.db` 一个文件**，而刚写下的结果落在 **`-wal`** 里
（本仓自己记着那条规矩：三个文件一起拉）。**修好之后：**

| 输入 | 从 `am start` 到结果落库 |
|---|---|
| `2+2` | **2183 ms**（debug 包） |
| `factor(1000000000000000003)` | **超过 2 分钟，轮询窗口内没出结果** |

⚠️ **这两个数要读准：**

- 第一个**不是求值耗时**，是**端到端**——冷启动（debug 1.75 s）+ 求值 + 落库 + 我 0.3 s 的轮询粒度。
  要单拎出求值，得先减掉冷启动，而那一步在 debug 上噪声很大；
- 第二个说明的是**那个输入很重**（半素数），而不是"引擎慢"——
  **超过窗口**既可能是引擎在算，也可能是应用的引擎超时把它掐了，**这两种我没有分开**。

**所以这一格仍然只是"端到端"那一个数**，设备侧的**纯求值**延迟还是没有——
但探针现在是**对的**（三个文件一起拉），下一个要量的人可以直接用。

#### 又试了一次，仍然没拿到——而这次的结果本身有信息量

换一个**中等重量**的输入想让它落在噪声之上：

| 输入 | 结果 |
|---|---|
| `2+2` | 2183 ms（端到端） |
| `factor(1000000000000000003)` | **> 2 分钟，没出结果** |
| `sum(1/x^2, 1, 200000, x)` | **> 2 分钟，没出结果** |

✅ **那"两种可能"查清了，而且答案是第三种：两者都不是。**

`calculator_controller.dart` 里 `engineTimeout` 的默认值是 **`Duration(seconds: 5)`**（⚠️ 引用的那一行本轮在
`:266`——**按名字找，别按行号找**：同一天里，这个文件因为别处的注释插入把行号整体顶走了一次，
`verification.md` §5s 记着这条规矩与它的代价）。
所以"两分钟没出结果"的真相是：**应用在第 5 秒就放弃了这一发**，把它当成"引擎失败"处理——
而那条路**不写 `calculator_result`**。**"引擎还在算"这个可能被排除**：它在 5 秒时就被丢掉了。

**于是三次测量现在都读得通了：**

| 输入 | 端到端 | 走的是哪条路 |
|---|---|---|
| `2+2` | 2183 ms | 真算出来了（< 5 s） |
| `factor(1000000000000000003)` | 无结果 | **5 秒超时**被丢掉 |
| `sum(1/x^2, 1, 200000, x)` | 无结果 | 同上 |

⚠️ **而这带来一个对用户可见的结论**：**超过 5 秒的输入，结果行上不会留下任何东西**。
用户在屏幕上看到的是什么，**这一轮没有看**（零接触通道只看得到持久化的那几栏）——
**那是一件该去看的事**：一个"算不出来"与一个"正在算"在屏幕上长得一样，就是本条最反对的那一类。

**而"没出结果"这个现象本身值得记**：在真机上，一个中等重量的符号求和
**两分钟内不给答案，也不给错误**（屏幕上大概是「等待输入」那一类）。
**这是对用户可见的一件事，而它此前没有被记录过。**

## 六、⚠️ 去看了那一眼，找到一处真的缺陷（2026-09-30）

第五节末尾写着「用户在屏幕上看到的是什么，这一轮没有看……那是一件该去看的事」。
**去看了**，把那三个输入里最重的一个写进去、启动、**等 12 秒**（远超那 5 秒 `engineTimeout`）后截图：

| 屏幕上那一栏 | 内容 |
|---|---|
| 表达式 | `Σ_{x=1}^{200000} 1/x²` —— **排版完全正确，用户打的式子没有问题** |
| 结果行 | **「= 等待输入」** |
| 错误行 | **「表达式需要修正 · 函数需要括号」** |

### 真相与它说出来的话，差得很远

**用户看到的是"我的括号打错了"——而他的括号没有错。**

引擎算了 5 秒、被应用放弃，于是**回落到旧解析器**；旧解析器读不懂 `sum(...)`，
就报了它自己那句 `needs (`。**所以这不是"超时没提示"，是"超时被报成了一个语法错误"。**

用户会去找一个**不存在的括号问题**——**这正是本仓最反对的那一类：一句话说岔了。**
（与前面那几个"看着像答案的错值"同族，只是错在诊断而不是错在数值。）

### 修法（下一轮的，形状已经清楚）

- `_askEngine` 的超时分支**已经有一条明确的失败理由**（`engine_timeout: 5000ms`）；
- `_friendlyCalculationError` 里已经有十一句同类的话（缺右括号、未知函数……），
  **欠的只是"超时"那一句**；
- 以及**让提交路径别把它当成"引擎没答案"回落掉**——超时是一个**确定的结论**
  （"没在 5 秒内算出来"），不是一个"这一次没有引擎答案"。这与 `unit_mismatch` 那一支同形：
  **引擎给了确定回答时，回落旧解析器只会得到一句说岔了的话。**

⚠️ 三条都写在这里，**没有动手**：这一轮的量已经做完，而改它要动提交路径的取舍规则
（那是本项目最重的一段代码），**半途改它比不改更坏。**

### ⚠️ 补记（同一天）：我试着改它，然后**退回来了**——因为它是**故意的**

第六节那处缺陷我动手改了（超时时抛出「引擎没在时限内算完」，提交路径与边打边算两条路一致）。
**改完之后三条测试当场红**，而它们的名字说明了一切：

```
calculator_engine_submit_test.dart      an engine that never answers times out and falls back
calculator_engine_live_test.dart        引擎永远不回答时屏幕照常有旧解析器的结果，超时之后这一发被释放
calculator_engine_submit_lifecycle_test.dart  a reply that arrives after a timeout does not overwrite the fallback
```

**"超时回落旧解析器"是被三条测试钉住的、刻意的设计**，不是疏忽。我的改动与它冲突。

**所以全部退回**（工作区与 HEAD 逐字节相同，1798 条全过）。

**而这不是"白做了一轮"**——它把这条发现的**性质**说清楚了：

## 八、设备侧求值延迟：**把这一项收成它真正要回答的那个问题**

此前它挂着"没量成"。逐个问一遍它究竟要回答什么：

| 它可能回答的问题 | 现在有没有答案 |
|---|---|
| 典型输入在设备上要多久？ | **量级已知，不必再量。** 宿主 0.02–16 ms（§3），设备是同一份库、换个 CPU，**差一个常数因子**；而应用的超时是 **5 秒**——离这个量级有三四个数量级 |
| 会不会有输入慢到用户等不了？ | **有答案，而且是量出来的**：`sum(1/x^2, 1, 200000, x)` 在设备上 **> 5 秒被放弃**（§5、§6 的截图） |

**所以这一项不是一个"还没测的数"，是一个"测了也不知道要干什么"的数。**
把它继续挂着，只会让每读一次对照表的人都以为缺一块——
**而缺的那一块已经被另一个更靠近决策的数（超时那一条）覆盖了。**

⚠️ **仍然如实标着**：设备上**单次求值的毫秒数**没有。谁哪天真的需要它
（比如要判断"预热引擎有没有用"），探针是现成的、修好的（`§5` 那段），
**缺的只是一个落在 0.3 秒到 5 秒之间的输入**——那是拿几个候选在宿主上先排一遍就能挑出来的事，
不是一件需要设计的事。

**这一条从"未测"改成了"不需要测（原因如上）"——两者在待办清单上的含义完全不同。**

## 十、⚠️ 那条关键词方法本身：**"0" 是可靠的，"非 0" 不是**

本文所有「HiPER 手册里 X 命中为 0」都是 `grep -oic` 数出来的。**这一轮拿它反过来自查了一次**，
而它当场给出一个假阳性：

| 词 | 命中 | 逐条看上下文之后 |
|---|---|---|
| `script` | **6** | 全是 `sub**script**` / `de**script**ion` / `super**script**`——**根本没有"脚本"这个功能** |
| `camera` | 6 | ✅ **逐条看过了：是真题**（手册 728–745 是"拍照取式"一整节，含相册导入） |
| `photo` / `scan` | 0 | 手册里它写的是 `camera` |
| `solve` | 1 | 与"solve 命中为 0"一致 |
| `currency` / `tax` / `loan` / `photo` / `scan` | **0** | —— |

### 为什么这个不对称很重要

- **子串匹配会多报**（`script` 那条就是），所以**非 0 的命中必须逐条看上下文**才能当结论；
- 而**它不会少报**：一个词真的出现过，任何子串形式都会命中至少一次。
  ⇒ **"命中为 0"是可靠的** —— 一条子串都没匹配上，全词更不可能。

**所以本文那些 `= 0` 的结论站得住，而凡是写成"它有"的，都要先看上下文。**
（`camera` 那 6 条**已经逐条看过了**——手册 728–745 行是"拍照取式"一整节，
所以第一节那张表里那一行现在是**实测口径**，不是"未量"。）

⚠️ **这也是一条给下一轮的话**：这份文档里凡是以**否定**形式写的（"命中 0"、"我们没有"）
都可以直接引用；凡是**肯定**形式的，用之前先把那几行原文调出来看一眼——
**我这一轮就是靠这一步才发现 `script` 是个假的。**

## 十一、⚠️ 那条"我们不达标"的实测：**是真的**（而我一度把它撤回了，那一步是错的）

### 事实

`androidTapTargetGuideline`（Flutter 自带，每个可点目标 ≥48dp）在主屏上**不通过**——
**但「不通过的是什么」这一节此前记错了，2026-10-10 逐个数过一遍，下面全换成实测的。**

**结构（读 `keypad/calculator_keypad.dart` 的 `_row` 定的）**：键盘是 `ColoredBox > Padding(6) > Column`，
Column 的每个孩子是一个**行组**，行组两片——`Expanded(flex: 2, _band)` 在**上**、
`Expanded(flex: 5, _mainStrip)` 在**下**。上面那片是**标签横带**（一行小字，`_bandCell` 每格各自可点），
下面那片是**主键条**（每颗键各自可点）。横带标的是**它下面那行**键的功能——HiPER 的机制。
**两片各自可点、各做各的事，而且两片都矮于 48。**

实测（360 × 800）：横带格 **66.6 × 15.0**、键 **66.6 × 42.1**、行组 66.6 × 57.1。

**六种尺寸逐个量（不合规节点数 / 键的高）**：

| 尺寸 | 不合规节点 | 键的高 | 横带格的高 |
|---|---|---|---|
| 320×640 | 73 | 29.0 | 9.8 |
| 360×640 | 73 | 29.0 | 9.8 |
| 360×800 | 73 | 42.1 | 15.0 |
| 393×851 | 73 | 46.3 | 16.7 |
| 411×731 | 73 | 36.4 | 12.8 |
| **412×915** | **25** | **≥48（达标）** | 18.8 |

⚠️ **所以旧文那三处都站不住**：
1. **`48.3` 是 320 宽屏幕上的「键宽」**（那里键是 48.3 × 29.0），不是 360 × 800 的——两个设备的数被拼到了一起；
2. **`24.2` 在测过的任何一个尺寸上都查不到**（键高见上表）；
3. **「在每一个测过的尺寸上都不通过」是假的**：**412 × 915 下不合规的只剩 25 个（全是横带格）**，
   键在那里**高过 48**。笼统一句「都不通过」把两种不同的成因混成了一条。

**没有任何一个有屏幕的手机躲得过它**这句话也得改：**412 × 915 那一档，主键条是达标的。**
躲不过的是**横带**——它每一档都矮于 48。

⚠️ **另外，当时这一节还把两处「本应用自己的」缺陷和键盘混在一起了**：显示区状态行里那颗 ☰
实测语义节点 **40 × 40**、`More...` **111.7 × 34.0**——**都不是 HiPER 的排布**，是纯缺陷，
2026-10-10 已修（状态行 40 → 48dp；连带 `CalculatorDisplay` 的固定部分 74 → 82dp、
高度下限 176 → 182dp，推导在那个组件的类注释里）。
所以本节原来的定位「本文里**唯一一条我们明确不达标**的地方」也要收窄：
**键盘的横带是权衡，那两颗按钮是缺陷，两者当时被记成了一条。**

### ⚠️ 而我一度把它撤回了——两次量错，方向相反

| 第几步 | 我做了什么 | 错在哪 |
|---|---|---|
| 1 | 用**默认测试面 800×600** 量，报「每行 26 dp 不达标」 | 尺寸确实是测试面的（那一档量到键 154.6 × **25.9**、横带 154.6 × 8.5）。**但接着写下的「真机上是 24.2 dp，量级一样」是编的**——24.2 在任何尺寸上都量不到（真机各档键高 29.0–46.3）。**用一个没量过的数去给一个量错的数作证。** |
| 2 | 改成真机尺寸重量，**"通过"了** ⇒ 判定第 1 步是假象，**撤回了整条发现** | **我以为在量 tap-target，其实那份文件断言的是 `labeledTapTargetGuideline`**——两条判据，我拿一条的通过去否掉另一条的不通过 |
| 3 | 按尺寸逐个量 | 结论「不通过」是对的（五档都是 73 个节点；412 × 915 是 25 个），**但「所有尺寸都不通过」和那个 24.2 都是错的**——见上表 |

**所以第 2 步才是错的那一步，而它错得比第 1 步更彻底**：
第 1 步只是把真机尺寸量成了测试面；**第 2 步把一条真发现撤回了**。

### 三条都很具体，值得写在同一个地方

1. **`meetsGuideline` 的失败是异步上报的**——`expect(...)` 不抛异常，
   测试在结尾才红。所以"用 try/catch 包起来看它过不过"**看不到任何东西**（我试过，
   五次都打印 PASS，而五次都红）。
2. **两条判据不能互相作证**：`labeledTapTargetGuideline` 过，
   **完全不能说明** `androidTapTargetGuideline` 也过——它们问的不是同一件事。
3. **量尺寸的东西必须自己设 `physicalSize`**（本仓已有先例：`tool_result_label_lengths_test.dart`）。

### 为什么**键盘那部分**仍然没有修

**横带每一档都矮于 48**（9.8–18.8），**主键条在矮屏上也矮**（29.0–46.3，412 × 915 那档达标）。
而**加高任一片都会挤动整块键盘**，那块键盘是**照着 HiPER 排的**（既定目标）：
横带标的是它下面那行键的功能，两片的高度是同一个行组里按 flex 2:5 分的，动一片就是动全盘。
所以"让它达标"与"保持与 HiPER 一致"**是一对要权衡的东西**——
而判据是 Flutter 的，不是这个仓的：**本文只负责把它量出来，不替仓主决定要不要让路。**

（**那两颗按钮不属于这一类，所以它们修了**——见上：它们不是 HiPER 的排布，是缺陷。
"是权衡所以不改"这句话**不能拿来豁免缺陷**，本节原来就是在这儿把它们混成一条的。）

**数在上面；几何在 `keypad/calculator_keypad.dart`**（`_row` 的那两片、`_bandCell`、`_keyButton`），
行与标签的**表**在 `keypad/hiper_keypad_function_rows.dart`——旧文把指针指到了表上，几何不在那里。
